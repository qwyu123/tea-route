# 茶途智配 · 演示原型 v0.1

安吉春茶电商订单的**归集**与**发运调度**决策辅助系统。演示用，单文件前端，双击即开。

---

## 怎么打开

双击 `index.html`（Chrome / Edge）。

- 顶部四个页签切换：订单池 → 渠道能力 → 调度方案 → 对比诊断
- 右上角圆钮切日夜；也可以在地址后面加 `?theme=dark` 直接开暗色
- 想直接给人看某一页：`index.html#plan`、`index.html#compare`

没有后端、没有登录、不联网。数据写在 `app.js` 里，改完刷新就变。

---

## 四个页面在讲什么

| 页面 | 想让人看到的事 |
|---|---|
| **订单池** | 合作社的单散在微信群、电话、一张会串行的表格里。左边是原始形态，右边是结构化结果。 |
| **渠道能力** | 六条渠道的报价、时效、限制、覆盖。**这是系统的地基，也是别人抄不走的部分。** |
| **调度方案** | 两段式：先把村里的件集到县城（客货邮 / 自送），再按去向分拨（专线 / 快递）。凑不上专线起运量的，明写差几件。 |
| **对比诊断** | 原方式 vs 方案：钱省了多少、从哪省的、以及**省不下来的部分是什么**。 |

## 数据与算法

全部现算，不写死。改 `app.js` 里的 `ORDERS` 或 `CH`，刷新就重算。

**计费口径：一律按包裹计。** 同一客户的多件可以合成一个批次，但包裹数单独记——快递首重是按包裹收的，这是"逐单发货"最隐形的一笔浪费。

| 渠道 | 报价 | 时效 | 关键限制 |
|---|---|---|---|
| 春茶专线 | 5.0 元/包 | 次日 | **20 包起运**，四向（杭沪京穗） |
| 顺丰 | 首重 18 + 续重 6/kg | 次日 | 全国 |
| 中通 | 首重 8 + 续重 3/kg | 2 日 | 全国 |
| 韵达 | 首重 7 + 续重 2.8/kg | 2 日 | 仅华东及一线 |
| 邮政 EMS | 首重 12 + 续重 4/kg | 2–3 日 | 全覆盖 |
| 客货邮 | 3.5 元/包 | 一天一趟 | **只跑村点 ⇄ 县城**，不发省外 |
| 自有车送县城 | 40 元/趟 | — | 装满才划算 |

**归集逻辑：**

1. 按取货点汇总，比较"客货邮带货"与"自有车跑一趟"，取便宜的
2. 按收货城市分组，组内包裹数 ≥ 20 且方向在专线覆盖内 → 发专线
3. 否则降级：次日件走顺丰，常规件走韵达（覆盖内）或中通
4. 每组都把"为什么选它 / 为什么没选专线"写出来，交给人判断

**跑出来的结果（当前样本 24 单 / 67 包）：**

- 计费成本 ¥1052.0 → ¥567.5，降 46.1%
- 发运批次 24 票 → 9 批
- 人工工时 118 分钟 → 33 分钟
- 杭州 26 包、上海 21 包够上专线；北京 9 包、广州 6 包不够，老实付快递首重，一分没省

## 哪些是示例数据（必须替换）

演示前请记住这一条：**除了安吉的地理和白茶分级，其余全是构造的。**

- **写实部分**（可按公开资料核对）：安吉 4 街道 8 镇 3 乡；安吉白茶是绿茶、品种白叶一号、分精品/特级/一级/二级；核心产区溪龙乡黄杜村
- **示例部分**（一律要换成真实数据）：24 张订单、客户名、每一条渠道的报价与时效、起运量门槛、专线截单时间、自有车成本
- 报价是按市场常见量级估的，**不是询价结果**。页面上已标"示例数据"，别在答辩时把它说成调研数据

## 答辩时可以这么讲

> 这个系统不做运输，只在一个决策点上做判断：**这批单该拆成几个批次、每个批次走哪条线**。它做两件事——把散单归集成够得着专线起运量的批，把够不着的差额老实写出来。

三个大概率会问到的问题，答案是现成的：

1. **"这跟普通快递比价工具有什么不同？"** —— 比价工具假设你一件一件发；这里的核心是"凑"，凑得够才有 5 元/包，凑不够就回去付首重。判断的是批，不是件。
2. **"省 46% 可信吗？"** —— 不可信的部分我已经剔掉了：北京、广州两批因为不够起运量，成本一分没降。46% 全部来自杭州、上海两批的合批与专线。
3. **"模型简化到什么程度还有意义？"** —— 只覆盖集货 + 干线分拨，不含采购、仓储、末端派送。前提是渠道报价稳定、单日发件量可预判。超出这个范围就不成立，这一点写在"对比诊断"页的边界里。

## 接口（给外部系统调用）

网页是给人看的，接口是给别的程序调的——飞书机器人、企微、小程序、以后接的树莓派，都从这一层进来。

```bash
python server.py        # 默认 http://127.0.0.1:8787，纯标准库，无依赖
```

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/health` | 健康检查 |
| GET | `/api/channels` | 渠道能力表 + 专线起运量 |
| GET | `/api/sample` | 内置的 24 单样本 |
| POST | `/api/plan` | 传订单，返回归集与分拨方案 |
| POST | `/api/parse` | 传一段口语化文本，返回结构化订单 |

```bash
# 把一段乱话变成订单，再直接算方案
curl -X POST http://127.0.0.1:8787/api/parse \
  -H "Content-Type: application/json" \
  -d '{"text":"溪龙 黄杜 明前特级 8 件 发上海，明天要到，共 5kg"}'

curl -X POST http://127.0.0.1:8787/api/plan \
  -H "Content-Type: application/json" -d '{}'     # 不传 orders 就用样本
```

**口径和网页完全一致**：同一套渠道表、同一个 `cost_of` 公式、同一套归集规则。已核对：24 单 67 包 → ¥567.5 / 省 46.1% / 9 批，两边一模一样。改价时两处要同步——`app.js` 的 `CH` 与 `server.py` 的 `CHANNELS`。

**`/api/parse` 的诚实说明：** 它是规则版（正则 + 关键词 + 别名表），不是模型。四句话里有一句"不着急"就不会误判成加急，但遇到没见过的客户简称照样认不出，会标成"未识别客户"并在 `inferred` 里说明。这正是下一步接模型的位置。
